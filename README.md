# 포한 · Forhan

한글이 없는 사람들을 위한, 맥과 윈도우용 독립 문서 편집기입니다. 한컴 설치나 계정 없이 로컬에서 실행합니다.

로그인·어시스턴트·온라인 번역·한컴 애셋·추가 기능·문서 보내기는 메뉴와 리본에서 제거했습니다. 기본 맞춤법 사전의 자동 다운로드도 끕니다. 문서 열기·편집·저장과 HWP/HWPX/PDF 출력은 계정이나 인터넷 연결 없이 사용합니다. 이 서비스 제거는 원본 한글 UI와 의도적으로 다른 부분입니다.

[실제 배포 앱의 오프라인 검사](research/evidence/line-grid-offline-runtime.json)는 Windows 배포 앱의 Chromium 네트워크를 오프라인으로 설정하고 모든 메뉴, 한글 편집, HWP/HWPX/PDF 저장을 확인했습니다. 편집기 준비 후 해당 작업 구간의 Chromium NetLog에서 외부 HTTP·WebSocket 요청은 없었습니다. 이 기록은 시작 시점이나 운영체제 전체 통신을 포함하지 않습니다.

## 실행 및 빌드

Node.js 24 이상과 npm을 사용합니다.

```sh
npm ci
npm start
```

```sh
npm run typecheck
npm test
npx playwright install chromium
npm run test:ui
npm run dist:win
```

macOS에서 `npm run dist:mac`으로 DMG/ZIP을 만듭니다. `.github/workflows/build.yml`은 Windows와 macOS에서 별도로 테스트하고 빌드합니다. 서명·공증 인증서는 포함하지 않습니다.

배포한 앱 자체의 검사는 빌드 후 `npm run test:packaged`로 실행합니다. 이 검사는 실제 실행 파일의 CPU 종류와 현재 빌드 파일의 일치를 먼저 확인하고, 개발 서버 없이 배포 앱으로 저장·재실행·인쇄 콜백·PDF·설치 글꼴을 검사합니다. 결과는 `release/validation/`에 기록합니다. CI는 Windows x64, macOS Intel x64, Apple Silicon arm64를 각각 같은 CPU의 실행 환경에서 검사하며, 통과해야 배포 파일을 업로드합니다. Mac CI 빌드는 임시 서명과 `codesign` 무결성 검사를 사용하며 Developer ID 서명·공증을 의미하지 않습니다. 세 환경의 실제 실행 검사를 진행 중이며, `391b6ec`의 입력 위치·장평 편집 집중 검사 3개씩은 [실제 CI 실행](https://github.com/aodjo/forhan/actions/runs/41342813689)에서 통과했습니다. 이 결과는 전체 UI·글꼴·배포 앱 호환성 통과를 뜻하지 않습니다.

Mac CI는 원본 `1440×1100` 창을 담을 수 있는 실제 비례 배율 1의 화면을 준비합니다. 기존 화면 모드가 부족하면 작업이 소유한 CoreGraphics 보조 화면을 만들고 검사 창을 해당 화면으로 이동합니다. 원래 주 화면을 유지하며, 종료 시 원래 화면 배치와 프로세스 종료를 독립적으로 확인합니다. 실제 화면 생성·복원 실패는 검사 실패로 남기며, 기대 좌표나 테스트 창 크기를 줄이지 않습니다. 이 보조 코드는 CI에서만 컴파일되고 배포 앱에는 포함되지 않습니다. 네이티브 API 선언의 출처는 Chromium이며 [해당 BSD 라이선스](licenses/chromium-display-tests-LICENSE.txt)를 보관합니다.

맑은 고딕이 없는 환경에서는 포함된 `Fhan Sans KR`의 일반·굵은 글꼴로 한글 폭을 보존합니다. 이 글꼴은 Noto Sans KR 2.004의 윤곽을 유지하고 현대 한글 11,172자와 한글 대체 글리프의 전진 폭을 한 글자 크기에 맞춘 OFL 파생 글꼴입니다. 설치된 원래 글꼴을 우선 사용하며 문서의 글꼴 이름과 7개 언어별 글꼴 표는 그대로 저장합니다. HTML과 인쇄용 문서에는 필요한 글꼴과 전체 라이선스를 자체 포함하며 온라인 글꼴 다운로드는 하지 않습니다. 이 범위는 원래 글꼴의 자형이나 모든 문자·글꼴의 완전한 동일성을 뜻하지 않습니다.

글꼴의 원본 버전·해시·변경 범위는 [출처 기록](licenses/fhan-sans-kr-provenance.json), 사용 조건은 [OFL 라이선스](licenses/fhan-sans-kr-OFL.txt)에 기록합니다. 고정된 원본 파일을 준비한 후 다음 TypeScript 명령으로 포함된 글꼴을 재생성할 수 있습니다. 원본 파일의 해시가 다르면 변환하지 않습니다.

```powershell
node scripts/build-korean-font.ts NotoSansKR-Regular.otf src/assets/FhanSansKR-Regular.otf regular-font-provenance.json
node scripts/build-korean-font.ts NotoSansKR-Bold.otf src/assets/FhanSansKR-Bold.otf bold-font-provenance.json
```

실제 Windows 한국어 입력기 검사는 `npm run test:ime:windows`로 실행합니다. 빌드된 Windows x64 배포 앱, 설치된 한국어 입력기와 대화형 세션이 필요합니다. 검사에서 만든 전경 창에만 운영체제 키 입력을 보내며 창의 소유권이나 포커스가 바뀌면 중단합니다. 시스템 입력기 설정을 변경하지 않으며, 전제 조건이 없으면 실패로 보고합니다. 결과는 `release/validation/windows-ime-win32-x64.json`과 해당 실행의 개별 원문·입력·출력 기록에 남습니다.

- 최근 문서와 디스크 자동 복구

새 문서는 HWPX를 기본으로 저장하며 저장 형식 목록은 HWPX → HWP → FHN 순서입니다. 이미 연 문서의 저장 형식은 유지합니다. 기존 `.forhan` 문서는 계속 가져올 수 있으며 포한 형식의 새 저장 확장자는 `.fhn`입니다. 첫 저장은 위치를 선택합니다. 가져온 파일을 자동으로 덮어쓰지 않습니다. `.fhn` 파일에는 편집 내용과 가져온 원본 데이터가 함께 들어갑니다. 수정하지 않은 HWPX는 원래 패키지 항목을 보존하고, 수정한 문서는 기존 XML과 편집 가능한 요소를 결합해 저장합니다.

HWP 저장은 한컴 실행 파일 없이 실제 HWP 5 바이너리를 생성합니다. 문단, 글자 서식, 표, 그림, 목록, 하이퍼링크를 독립적으로 읽고 저장하며, 수정하지 않은 HWP는 원본 바이트를 그대로 보존합니다. 암호화·배포용 HWP는 현재 읽지 못합니다. 수식·일부 도형과 같이 편집기가 해석하지 못한 개체는 원본을 유지하는 개체로 표시합니다. 변경한 문서의 지원하지 않는 바이너리 개체를 내보낼 수 없을 때는 저장을 중단하고 알립니다. 이때 포한 형식으로 작업을 보관할 수 있습니다. 한글과 동일한 조판·페이지 배치를 보장하지는 않습니다.

## 한글 화면과의 일치

설치된 한글 2024의 1440×960, 96 DPI 화면을 기준으로 제목 표시줄, 메뉴, 리본, 서식 도구, 눈금자와 상태 표시줄의 위치를 측정해 구현합니다. 아이콘은 독립적으로 작성한 SVG입니다. [직접 캡처 비교](research/ui-reference/visualcomparison-quickbar-glyphs.json)의 기본 화면은 전체 96.57%, 빈 작업 영역을 제외한 화면 구성 요소는 90.23%의 픽셀이 동일했습니다. 이 비교는 삭제한 온라인 서비스 영역도 제외하지 않습니다. 빠른 도구의 문단 스타일과 정렬 아이콘 7개는 각각 해당 16×16 영역의 픽셀이 일치하지만, 서식 도구줄 전체는 85.22%입니다. 이 수치는 Windows의 빈 문서 화면 한 장에 대한 비교이며, macOS의 화면 일치나 모든 한글 메뉴 기능의 구현을 보장하지 않습니다.

Windows 실행·저장·네이티브 창 동작은 실제 환경에서 검증합니다. macOS Intel·Apple Silicon에서도 CI의 실제 Electron 창으로 검사하고 있으나, 글꼴 대체와 전체 UI·배포 앱 검증은 아직 완료되지 않았습니다.

최소 공백 구현 당시의 문단 모양 대화상자는 해당 Windows 배포 앱에서 별도로 비교해 90.57%의 픽셀이 일치했습니다. 그 배포본의 핵심 109개·화면/데스크톱 121개·배포 앱 17개 검사와 실제 Windows 한국어 입력기 5개 시나리오가 통과했으며, 저장한 HWP/HWPX 112개를 설치된 한글에서 다시 열어 서식과 원문을 확인했습니다. 기본 화면의 일치율을 모든 대화상자와 기능의 일치율로 해석할 수 없으며, 전체 UI 100% 일치는 아직 달성하지 못했습니다. [해당 대화상자 비교 기록](research/ui-reference/visualcomparison-paragraph-minimum-space.json)에 원본·대상 해시와 비교 범위를 남깁니다. 이후 문단 미리 보기의 검증은 아래 별도 기록을 따릅니다.

글자 모양 대화상자의 별도 비교는 93.75%입니다. [글자 모양 비교 기록](research/ui-reference/visualcomparison-character-dialog.json)은 원본 창과 직접 캡처한 포한 대화상자를 이미지 수정이나 정렬 보정 없이 비교합니다. 이 수치 역시 해당 Windows 화면 상태 한 장에 대한 결과입니다.

글자 모양의 [확장 탭 두 상태](research/ui-reference/visualcomparison-character-decorations.json)는 원본과 같은 695×570이며, 전체 94.93~95.01%의 픽셀이 일치했습니다. 원본 PNG를 수정하거나 정렬하지 않고 비교했으며, Chromium과 Electron의 독립 디코더가 같은 일치 픽셀 수를 계산했습니다. 밑줄 위치는 운영체제 기본 선택창 대신 원본과 같은 91×88 목록을 사용하며, 픽셀 일치율은 90.72%입니다. 없음·아래쪽·위쪽을 선택할 수 있고, 가져온 가운데 밑줄은 별도 항목으로 보존합니다. 밑줄·취소선 모양 목록은 각각 원본과 같은 91×348, 91×322입니다. 강조점과 테두리/배경 탭, 다른 플랫폼·DPI의 일치는 미완료입니다.

이전에 기록한 확장 탭 98.15~98.16%와 빈칸·커닝 영역의 픽셀 일치 주장은 디코딩한 픽셀 자료를 문자열로 덮어쓴 비교 도구 오류로 철회합니다. 아래 TypeScript 비교 도구는 실제 픽셀 버퍼와 크기를 검사하며, 같은 오류를 재현하는 회귀 검사를 포함합니다.

색 선택창 6개 상태는 설치된 한글의 실제 창과 크기가 일치하며, 직접 캡처한 픽셀 비교는 약 86.6~93.0%입니다. [색 선택창 비교 기록](research/ui-reference/visualcomparison-color-palettes.json)에 상태별 결과가 있습니다. 화면 색 골라내기는 API 연결과 취소 처리를 구현했으나 실제 OS 화면 선택은 아직 검증하지 못했습니다. 테마 관리 하위 메뉴, 다른 테마·DPI·플랫폼의 일치는 미완료입니다.

## 검증과 분석 기록

`research/`의 캡처·분석·네이티브 검증 자료는 로컬에 보관하며 Git과 배포 파일에서 제외합니다. 아래 해당 경로의 링크는 로컬 분석 자료를 가리킵니다. 원본 PNG 두 장의 전체 RGB 픽셀 비교는 다음 명령으로 다시 실행할 수 있습니다. 크기가 다르면 정렬하거나 축소하는 대신 실패합니다. 흰 배경도 일치율에 포함됩니다.

```sh
node scripts/compare-ui.ts native.png forhan.png
```

설치된 한글 2024에 대한 REA 분석과 실제 한글을 통한 왕복 검증은 [research/hancom-analysis.md](research/hancom-analysis.md)를 참고하세요. 네이티브 검증용 문서는 별도 한글 인스턴스에서 생성했고 배포물에 포함하지 않습니다. 독립 구현에는 한컴 바이너리, 글꼴, 아이콘, 문서 양식을 포함하지 않습니다.

글자 크기의 실제 단위 변환과 고정 줄 간격은 포한이 만든 HWP/HWPX 10개를 설치된 한글에서 열고 다시 저장해 확인했습니다. 13.25pt를 대화상자에서 반올림하거나 고정 18.25pt를 퍼센트로 바꾸던 문제를 수정했습니다. 이 검증은 해당 표본의 서식 보존에 대한 결과입니다.

추가 문단 표본 8개는 한글의 실제 문단 속성과 재저장 결과를 함께 검증했습니다. HWP에서 물리 단위와 글자 단위를 잘못 저장하던 문제를 수정해 12.25pt 여백, ±18.25pt 첫 줄 거리, 글자 단위 간격을 보존합니다. 내어쓰기는 첫 줄을 유지하고 다음 줄을 오른쪽으로 옮깁니다. 기본 문단 40개의 실제 한 쪽 PDF, 일반 구분선과 명시적 쪽 나누기의 구분, 편집·HTML·인쇄 문서의 계산된 스타일도 회귀 검사합니다.

글자 크기 추가 표본 12개는 1·3.25·200·5000pt와 가져온 0·0.5pt의 HWP/HWPX를 실제 한글에서 열고 재저장해 확인했습니다. 세 입력창의 임의적인 6~144pt 제한을 없애고, 13.25pt에서 키우기를 누르면 14.25pt가 되도록 맞췄습니다. 한글 파일의 정수 저장 범위를 넘으면 값이 뒤틀리는 대신 저장 오류를 알립니다. [글자 크기 네이티브 검증](research/evidence/character-size-native-oracle.json)과 [배포 실행 파일 검사](research/evidence/character-size-runtime.json)에 검증 범위를 기록합니다.

언어별 글자 비율 표본 6개도 실제 한글의 7개 언어 속성과 재저장 값이 일치했습니다. 자간·상대 크기·글자 위치는 편집과 HTML·PDF 출력에 적용하며, 다른 항목만 바꿀 때 기존 글꼴·크기·강조와 언어별 비율을 유지합니다. [비율 보존 검증](research/evidence/character-metrics-native-oracle.json)과 [실행 파일 검사](research/evidence/character-metrics-runtime.json)에 결과를 기록합니다. 장평의 실제 편집과 가로 폭 계산은 아래 장평 검증에서 별도로 다룹니다. 모든 문자 체계와 한글의 전체 조판 결과가 같다는 뜻은 아닙니다.

글자 음영 표본 8개는 한글에서 실제 글자 속성과 재저장 결과가 모두 일치했습니다. [네이티브 음영 검증](research/evidence/character-shading-native-oracle.json)과 [배포 실행 파일 검증](research/evidence/color-palette-runtime.json)은 흰색과 없음이 구분되고 글자 색과 독립적으로 유지됨을 확인합니다. 현재 문서·패키지 테스트 102개와 UI/Electron 테스트 106개가 통과했습니다. [실제 Windows 배포 앱 검사](research/evidence/packaged-validation-win32-x64.json)는 별도의 14개 검사 결과를 기록하며, 데스크톱 회귀 검사 13개를 배포 실행 파일로 다시 수행하고 실제 배포 프로세스의 신원 검사를 추가합니다.

줄 간격 표본 8개도 [실제 한글의 속성과 재저장 결과](research/evidence/line-spacing-native-oracle.json)가 일치했습니다. 비율은 5%씩, 고정 값은 다음 정수 pt로 증감하며, 표시가 18.3이어도 변경하지 않은 18.25pt 원본을 유지합니다. [배포 앱 검사](research/evidence/line-spacing-runtime.json)는 실제 저장 파일에서도 0%와 고정 0pt가 구분됨을 확인합니다. 목록 창은 비율 123×166, 고정 123×270으로 원본과 크기가 같고 [직접 픽셀 비교](research/ui-reference/visualcomparison-line-spacing.json)는 각각 92.04%, 94.62%입니다. 비율의 새 입력은 0~500%이며 고정 값은 현재 본문 높이를 기준으로 검사합니다. 이 고정 상한 계산은 관찰한 원본의 본문 높이와 일치하는 값에서 도출한 것으로, 모든 구역·표·실시간 용지 변경 동작의 일치를 뜻하지 않습니다.

글자 단위 간격은 설치된 한글의 기본 문서에서 10pt·20pt 글자 모두 CHAR 150이 7.5pt로 표시되고, 해당 물리 간격과 [같은 화면을 렌더링](research/evidence/relative-character-native-equivalence.json)함을 확인했습니다. 포한도 이 간격을 현재 글자 크기와 분리해 편집·HTML·인쇄에 적용하고 빠른 입력창에서는 pt로 편집합니다. 변경하지 않은 원본 글자 단위는 HTML 왕복 후에도 보존하며, 외부 HTML의 일반 em 단위와 구분합니다. [한글의 실제 재저장 표본 4개](research/evidence/relative-character-native-oracle.json)와 [배포 앱의 저장 검사](research/evidence/relative-character-runtime.json)를 기록했습니다. 다른 문서 기본 스타일·호환성 설정 전체의 단위 해석은 아직 검증하지 않았습니다. 위 화면 일치 수치는 한글 안에서의 단위 비교이며 포한 전체 UI 100% 일치를 뜻하지 않습니다.

여섯 문단 정렬은 [한글에서 실제로 열고 재저장한 표본 12개](research/evidence/paragraph-alignment-native-oracle.json)에서 모두 구분됐습니다. 배분은 글자 사이를, 나눔은 어절 사이를 넓히며 마지막 줄에도 적용합니다. [배포 앱 검사](research/evidence/paragraph-alignment-runtime.json)는 실제 글자 위치, 한 글자·한 단어의 경계 사례, Alt+1~6와 네이티브 저장을 확인합니다. [8개 상태의 직접 비교](research/ui-reference/visualcomparison-paragraph-alignment.json)에서 정렬 아이콘 6개는 각각 16×16 영역이 일치했고, 정렬 도구 영역 전체는 97.45%였습니다. 본문의 세로 위치·글자 렌더링·원본의 맞춤법 표시 등은 여전히 다르며, 이 아이콘 결과를 전체 UI나 본문 일치로 확대할 수 없습니다.

[첫 줄 배치의 32개 네이티브·배포 앱 표본](research/evidence/native-line-leading-runtime.json)은 10·16·20pt, 비율·고정 간격, 혼합 크기, 별도 문단, Arial·맑은 고딕과 한글 글자를 비교합니다. 16pt·160%에서 첫 글자가 9픽셀 아래로 밀리던 문제와 고정 0pt에서 줄마다 4픽셀씩 누적되던 밀림을 수정했습니다. 32개 중 22개는 측정한 첫 글자의 위쪽 좌표가 같고, 20pt를 포함한 10개는 1픽셀 차이가 남습니다. 글자의 픽셀 모양, 공백 폭, 전체 조판의 일치를 뜻하지 않습니다. 위·아래 첨자·그림·오른쪽에서 왼쪽으로 쓰는 문단은 이 기준선 계산을 아직 적용하지 않습니다. HTML·실제 PDF 출력의 공통 스타일, 클릭 위치·실행 취소·원본 서식 보존과 줄 바꿈도 회귀 검사합니다.

언어별 글꼴과 수치 표본 4개도 실제 한글에서 7개 언어 속성과 재저장 결과가 모두 일치했습니다. 글자 모양의 언어 선택에서 글꼴·자간·상대 크기·글자 위치를 따로 변경할 수 있으며, 대표 설정은 전체 언어에 적용합니다. 언어를 오가도 임시 값은 유지되고 취소하면 문서는 바뀌지 않습니다. [언어별 네이티브 검증](research/evidence/character-language-native-oracle.json)과 [배포 실행 파일 검사](research/evidence/character-language-runtime.json)에 범위를 기록했습니다.

‘글꼴에 어울리는 빈칸’은 문서 전체 호환성 옵션과 별개인 글자 설정입니다. 해제하면 반 글자 폭, 선택하면 글꼴의 원래 빈칸 폭을 사용하며 자간·상대 크기·장평을 반영합니다. [한글 왕복 표본 8개](research/evidence/character-spacing-native-oracle.json)와 [배포 앱이 실제 저장한 8개 파일](research/evidence/character-spacing-packaged-writes.json)은 빈칸과 커닝의 네 조합을 각각 보존합니다. [본문 32개 비교](research/evidence/character-spacing-runtime.json)에서는 빈칸 28개 표본의 8칸·16칸 뒤 글자 위치가 원본과 최대 2픽셀 차이였습니다. 일부 글꼴의 커닝과 장평 조판은 아직 다릅니다. 상대 크기 50·80·120%에서도 줄 높이는 원래 기준 크기를 사용하는 [한글의 실제 줄 정보](research/evidence/relative-size-native-line-cache.json)를 반영했습니다.

설치 글꼴은 창에서 처음 목록을 열 때 읽으며, 글꼴의 한글 이름과 실제 Unicode 문자 매핑을 사용합니다. 바탕체·굴림체처럼 여러 글꼴이 묶인 TTC는 해당 이름의 구성원을 찾아 표시합니다. 브라우저 권한이 없을 때는 기존 선택과 문서의 글꼴 이름을 유지합니다. [설치 글꼴 실행 검증](research/evidence/installed-font-runtime.json)과 [한글 재저장 검증](research/evidence/installed-font-native-oracle.json)에 결과를 기록했습니다. 글꼴 메뉴의 외형·분류·목록 순서는 한글과 완전히 같지 않으며, 한컴의 비공개 글꼴 모음이나 다운로드 기능을 복제하지 않았습니다.

이 저장소는 TypeScript strict 모드를 사용합니다. 기능별 브랜치에서 작업한 뒤 Conventional Commits 형식의 메시지로 병합합니다.

글자 외곽선의 없음·실선·점선·굵은 선·파선·일점쇄선·이점쇄선을 편집할 수 있습니다. [한글 원본 16개 읽기](research/evidence/character-outline-native-imports.json), [작성 파일 16개의 실제 한글 속성·재저장 검증](research/evidence/character-outline-native-oracle.json), [배포 앱에서 직접 편집한 파일 14개의 추가 한글 검증](research/evidence/character-outline-gui-native-oracle.json)을 통과했습니다. 그림자·밑줄·음영과 독립적으로 보존하며, 원래 글자를 유지한 SVG 윤곽선은 줄 바꿈·선택·입력·실행 취소와 HTML/PDF 출력에 적용됩니다. 한글 API의 목록에 없는 값 7도 HWP·포한·HTML에 유지하고, HWPX에서는 실제 한글과 같은 종류 생략 동작을 따릅니다. 화면·글꼴 전체의 한글 GDI 픽셀 일치나 다른 편집기의 클립보드 표시까지 보장하지 않습니다. [선택 목록의 원본 비교](research/ui-reference/visualcomparison-character-outline.json)는 같은 91×192에서 98.15%, 해당 기본 대화상자는 95.01%이며, 독립 디코더의 픽셀 수가 일치했습니다. 이 값은 원본 PNG를 보정하지 않은 해당 두 상태의 비교입니다.

글자 그림자의 없음·비연속·연속, X/Y 방향과 독립 색을 편집하고 미리 볼 수 있습니다. [한글 원본 12개 읽기](research/evidence/character-shadow-native-imports.json), [포한 작성 파일 12개의 실제 한글 속성·재저장 검증](research/evidence/character-shadow-native-oracle.json), [배포 앱에서 편집·저장한 파일 6개의 추가 한글 검증](research/evidence/character-shadow-gui-native-oracle.json)을 통과했습니다. 음수·0 방향과 꺼진 그림자의 설정도 HWP/HWPX에 보존하며, 혼합 선택에서 바꾸지 않은 종류·방향·색은 유지합니다. 화면·HTML·PDF는 같은 그림자 스타일을 사용하지만, 연속 그림자와 큰 글꼴의 픽셀 조판이 한글과 동일하다는 뜻은 아닙니다. [배포 실행 검사](research/evidence/character-shadow-runtime.json)에 실제 원본 12개 열기, 네이티브 저장 6개와 PDF 출력을 기록했습니다.

밑줄·취소선 [네이티브 생성 표본 28개](research/evidence/character-decoration-native-generated.json)를 분석하고, 수정한 HWP/HWPX 16개의 활성 선 위치·모양·색을 실제 한글의 속성과 재저장 결과로 검증했습니다. [배포 앱 검사](research/evidence/character-decoration-runtime.json)는 원본 28개 열기와 실제 저장 8개, 편집·HTML·PDF의 공통 선 스타일을 확인합니다. 글자 색이 섞인 선택 영역에서 기본 탭으로 밑줄을 켜면 한글처럼 검은 선을 사용합니다. 예전 가운데 밑줄은 HWP 재열기에서 한글과 같이 원래 색의 취소선으로 바뀌며, HWPX는 가운데 속성을 유지합니다. 독립적으로 다른 선 두 개가 가운데 겹친 경우 HWP 저장은 중단하고 HWPX·포한 저장을 안내합니다. 모든 글꼴·선 종류의 실제 조판이 동일한 것은 아닙니다.

글자 강조점의 없음과 12종 표시를 편집합니다. [한글 원본 32개 읽기](research/evidence/character-emphasis-native-imports.json), [작성 파일 32개의 실제 한글 속성·재저장 검증](research/evidence/character-emphasis-native-oracle.json), [배포 앱에서 직접 편집한 파일 26개의 추가 한글 검증](research/evidence/character-emphasis-gui-native-oracle.json)을 통과했습니다. 영문·숫자·한글의 글자별 위·아래·왼쪽 위치를 표시하며 공백을 건너뜁니다. 합쳐진 문자·이모지는 하나의 글자 묶음으로 다루고, 줄 바꿈·원문·선택·되돌리기를 유지합니다. HTML·실제 PDF 출력은 같은 그리기 방식을 사용합니다. 목록에 없는 원본 값 13~15는 HWP·포한·HTML에 보존하며 HWPX는 실제 한글처럼 종류를 생략합니다. 원본의 코드 3·4는 XML 이름과 화면 모양이 서로 뒤바뀌는 동작도 구분해 보존합니다. [선택 목록 직접 비교](research/ui-reference/visualcomparison-character-emphasis.json)는 같은 91×348에서 96.50%, 해당 기본 대화상자는 94.98%이며 두 독립 디코더의 픽셀 수가 일치했습니다. 모든 글꼴·세로쓰기·복합 조판의 네이티브 픽셀 일치나 Mac 실행 검증을 뜻하지 않습니다.

장평은 [공식 한글 도움말](https://help.hancom.com/hoffice130/ko-KR/Hwp/format/font/fonts%28scale%29.htm)의 50~200% 범위에서 편집하며, 대표·7개 언어 설정과 Alt+Shift+J/K를 지원합니다. [한글 원본 20개 읽기](research/evidence/character-width-native-imports.json)와 [작성 파일 20개의 실제 한글 속성·재저장 검증](research/evidence/character-width-native-oracle.json)에서 장평·자간·상대 크기와 외곽선·강조점·그림자·밑줄이 함께 보존됐습니다. 글자 높이와 원문을 유지하면서 가로 폭과 비례 자간을 계산하고 HTML·PDF에도 같은 그리기를 적용합니다. 실제 픽셀로 폭·높이 변화를 검사하고 Home·방향키 뒤 입력, 줄 바꿈과 한 번의 되돌리기도 확인합니다. 0·255 같은 가져온 값과 원본 단축키의 경계 동작도 별도로 보존합니다. 히브리어는 결합 부호와 브라우저의 양방향 순서를 보존하면서 화면 장평·자간을 적용합니다. 아랍어·인도계 등 연결 문자는 단일 서식의 완전한 어절에 장평·자간을 적용하며 원래 연결 모양과 결합 부호를 유지합니다. 서식 경계를 넘는 어절과 문단 폭보다 긴 어절의 화면 장평·자간은 계속 구현 중입니다. 모든 글꼴·문자 체계·DPI의 네이티브 픽셀 일치나 Mac 실행을 검증한 결과는 아닙니다.

[장평 배포 앱 검사](research/evidence/character-width-runtime.json)는 실제 한글 원본 20개 열기, 24개 화면 조건, 직접 편집한 HWP/HWPX 12개와 PDF 출력을 기록합니다. 이 12개도 [실제 한글의 속성·재저장 결과](research/evidence/character-width-gui-native-oracle.json)가 일치했습니다. [원본 잉크와 실제 배포 앱의 진행 간격 비교](research/evidence/character-width-advance-comparison.json)는 Arial 32pt·125% 배율의 장평 50/75/100/150/200과 자간 0/20 조합 10개에서 최대 0.07픽셀 차이입니다. 글자 모양 자체의 픽셀 일치를 뜻하지 않습니다. [기본 대화상자 비교](research/ui-reference/visualcomparison-character-width-basic.json)는 기존과 같은 695×570, 93.75%입니다. 실제 포터블 실행 파일에서도 장평·외곽선·그림자·강조점·빈칸 설정을 함께 바꾸고 한 번에 되돌리는 동작을 확인했습니다.

[히브리어 배포 앱 검사](research/evidence/hebrew-width-runtime.json)는 원본과 같은 5개 화면 조건, 실제 장평 대화상자로 작성한 HWP/HWPX 8개, PDF 출력과 혼합 문장의 클릭·단어 선택을 기록합니다. 8개 파일은 [실제 한글로 다시 열어](research/evidence/hebrew-width-native-oracle.json) 원문과 7개 언어의 장평·자간·상대 크기가 일치했습니다. [원본 잉크 비교](research/evidence/hebrew-width-geometry-comparison.json)는 Arial 32pt·125% 배율에서 가로 시작점 4개 조건의 최대 오차가 1픽셀이고, 5개 조건의 잉크 상단은 같으며 하단은 최대 1픽셀 차이입니다. 음수 자간 조건은 잉크가 겹쳐 개별 글자 비교에서 제외했습니다. 히브리어가 섞인 문단에도 원래 글자 크기에 따른 세로 기준선과 줄 간격을 적용하며, 혼합 크기·자동 줄 바꿈·고정·0pt 간격과 폭을 좁혔다 넓히는 재배치를 검사합니다. RTL 단어를 선택한 뒤 빠르게 입력할 때 글자 순서가 뒤바뀌던 문제도 수정하고 실제 키 입력·저장·한 번의 되돌리기를 12회 반복 검사합니다. 전체 글꼴 픽셀 일치, 임의 문서의 페이지 구성, OS 입력기·Mac 실행 검증은 남아 있습니다.

장평이 적용된 문서의 마우스 드래그는 실제 원문 글자 영역을 논리적 선택 범위로 변환합니다. 양방향 혼합 문장의 정방향·역방향·부분 선택, 문단 경계·빈 문단, Shift 확장, 단어·문단 단위 선택을 검사하며, 서식이 나뉜 결합 문자와 ZWJ 이모지도 원래 문자 묶음을 유지합니다. 자동 스크롤은 마우스를 놓거나 Escape·창 이탈·문서 교체가 발생하면 중단됩니다. 표 안의 글자 선택과 셀 사이 선택도 구분합니다. [실제 Windows 배포 앱의 드래그·저장·되돌리기 검사](research/evidence/native-width-drag-runtime.json)와 [직접 저장한 HWP/HWPX 네 파일의 한글 재열기 검사](research/evidence/native-width-drag-native-oracle.json)는 원문과 7개 언어의 장평 75%·자간 20%·상대 크기 100% 보존을 확인합니다. 선택한 글자의 끌어놓기 이동, 터치·펜, 모든 OS 입력기와 Mac 실행은 이 검증 범위에 포함되지 않습니다.

HWP 저장 시 임의로 만든 줄 캐시 때문에 실제 한글에서 큰 글자가 겹치던 문제를 수정했습니다. 새로 작성하는 문단의 캐시 개수를 0으로 저장하여 원문·글꼴·서식을 기준으로 한글이 다시 조판하게 합니다. 변경하지 않은 원본의 바이트 보존은 유지합니다. [실제 한글 창의 14개 열기·재저장 검사](research/evidence/hwp-reflow-native-validation.json)는 배포 앱이 저장한 8개 파일과 빈 문서·표·목록·혼합 크기·그림 표본을 확인합니다. [HWP/HWPX 본문 비교](research/evidence/hwp-reflow-body-pixel-comparison.json)는 같은 한글에서 Arial 32pt·자간 20·장평 50/75/150/200%로 표시한 네 쌍의 원본 800×300 영역에서 RGB 픽셀이 일치했습니다. 이 비교 범위는 해당 원본 한글 본문이며, 포한 전체 UI와 모든 문서의 화면 일치 검증은 계속 필요합니다.

아랍어·힌디어·벵골어·태국어의 [원문 12개를 실제 한글에서 열고 재저장](research/evidence/joined-lines-native-oracle.json)해 Arial 32·16·24pt의 줄 기준선과 160%·고정 18pt·고정 0pt 간격을 확인했습니다. 아랍어 문단이 이 줄 계산을 건너뛰던 문제를 수정해, 기본 문단 방향에서도 양방향 문자 순서를 줄 바꿈으로 오인하지 않습니다. 원래 연결 모양과 결합 부호를 유지하며 편집·HTML에 같은 줄 배치를 적용합니다. [Windows 배포 앱 검사](research/evidence/joined-lines-runtime.json)는 12개 원문의 실제 글자 위치와 HWP/HWPX/HTML/PDF 출력을 확인합니다. 폭을 좁혔다 넓히는 재배치와 0pt 겹침도 별도로 검사합니다. 이 결과는 세로 배치에 대한 검증이며, 모든 글꼴의 한글 픽셀 일치는 계속 검증 중입니다.

연결 문자의 가로 장평은 완전한 어절을 함께 조합하고 글자 높이를 유지합니다. 부분 선택에서도 어절 전체의 조합을 유지한 채 선택한 글자만 흰색으로 표시하며, 원문 클릭·드래그·입력·한 번의 되돌리기와 HTML 재열기를 검사합니다. 확대된 아랍어가 앞 글자와 겹치던 문제, 문단 들여쓰기가 어절 안에 다시 적용되던 문제, 긴 문단에서 부분 선택 후 나머지 글자가 사라지던 문제도 수정했습니다. [실제 배포 앱 검사](research/evidence/contextual-width-runtime.json)는 원본과 같은 21개 화면 조건, HWP/HWPX 출력 24개와 PDF를 기록하며, 이 24개는 [실제 한글에서 다시 열어](research/evidence/contextual-width-native-oracle.json) 원문과 7개 언어의 장평·자간·상대 크기 보존을 확인합니다. [원본 잉크 비교](research/evidence/contextual-width-ink-comparison.json)는 Arial 32pt·125% 배율·자간 0·장평 75/100/150%의 여섯 문자열에 한정한 18개 조건입니다. 원본 PNG를 보정하지 않고 같은 영역에서 측정한 잉크 경계 차이는 최대 2픽셀이며 RGB 차이도 별도로 기록합니다. 전체 글꼴·문자 모양·UI 일치를 의미하지 않습니다. 이 검사는 자간 0의 어절 장평에 대한 결과이며, 비영 자간의 추가 검증은 아래에 기록합니다. 서식 경계·긴 어절, OS 입력기와 Mac 실행은 검증이 남아 있습니다.

양방향 혼합 문장의 자간은 원래 논리적 원문을 유지하면서 실제 한글의 방향별 진행 경계를 계산합니다. 아랍어·히브리어 앞의 빈칸, 같은 RTL 구간 안의 단어 사이 빈칸, 숫자·괄호와 마지막 빈칸을 구분합니다. 자간 −20/0/20의 42개 빈칸 조건, 부호가 있는 히브리어와 없는 히브리어의 글자 시작점, 오른쪽 정렬한 `é`와 `é`의 마지막 글자 위치를 실제 화면에서 검사합니다. 부호가 합성되지 않는 경우의 마지막 기본 글자 진행과 NFC로 합성되는 경우도 구분합니다. 빈칸 보정 때문에 자간 0에서 커닝이 달라지던 문제와 Electron에서 아랍어 뒤 빈칸이 이중 보정되던 문제도 수정했습니다.

[방향별 자간 배포 검사](research/evidence/directional-tracking-validation.json)는 실제 HWP/HWPX/HTML/PDF 출력과 [한글로 다시 연 파일 12개](research/evidence/directional-tracking-native-oracle.json)의 원문·7개 언어 설정 보존을 기록합니다. [원본 잉크 비교](research/evidence/directional-tracking-ink-comparison.json)는 Arial 32pt·125%·장평 100의 원본 PNG를 보정하지 않고 같은 좌표에서 측정했습니다. 구현된 히브리어·문장 끝 빈칸·아랍어 자간 0의 일곱 조건은 잉크 경계 차이가 최대 1픽셀입니다. 이 이전 검사에서 아랍어 자간 ±20 두 조건은 미완료로 기록했습니다. 아래 추가 검사는 이 두 조건과 연결 문자의 비영 자간을 포함합니다. 모든 줄 바꿈·글꼴, 방향 제어 문자의 한글식 표시, OS 입력기·Mac 실행과 전체 UI 일치는 계속 구현·검증 중입니다. Unicode 방향 해석에는 MIT 라이선스의 bidi-js 1.1.0을 사용하며 라이선스 원문을 배포 파일에 포함합니다.

연결 문자의 비영 자간은 완전한 원문을 한 번에 조합하고, 실제 글꼴의 독립적인 문자 묶음에만 진행 거리를 적용합니다. 필수 lam-alef 합자와 결합 부호를 분리하지 않으며, 아랍어 안의 아라비아 인도 숫자는 원래 왼쪽에서 오른쪽 순서를 유지합니다. 장평 75/100/150%·자간 −20/20의 다섯 원문 조건에서 실제 편집 원문 영역과 표시 글자의 위치·높이·뒤따르는 글자 진행을 검사합니다. 실제 한글 PDF의 글자 시작점도 별도로 대조합니다. 좁은 폭에서 어절 전체가 다음 줄로 이동하는 동작, 물리적인 마우스 클릭·단어 선택·입력·한 번의 되돌리기, HWP/HWPX·스크립트 없는 HTML 출력과 재열기도 검사합니다. [추가 배포 검증](research/evidence/contextual-tracking-validation.json)은 최종 Windows 실행 파일과 검사 결과를 연결합니다. [원본 화면 비교](research/evidence/contextual-tracking-ink-comparison.json)는 원본 18개를 보정 없이 같은 좌표에서 비교하며, [실제 한글 재열기](research/evidence/contextual-tracking-native-oracle.json)는 배포 앱이 저장한 HWP/HWPX 28개의 원문과 7개 언어 설정을 확인합니다. 이 18개 조건의 잉크 경계 차이는 최대 1픽셀이며 RGB 차이는 별도로 기록합니다. 모든 글꼴·전체 UI의 픽셀 일치, 서식 경계·긴 어절·임의 줄 끝의 자간 정책, 실제 OS 입력기와 Mac 실행을 보장하지 않습니다.

Windows 한국어 입력기는 Win32 가상키를 실제 운영체제 입력기가 처리하도록 실행해 검사합니다. 조합 과정, 겹받침 삭제, 다음 음절 재조합, 방향키·Enter·한 번의 되돌리기는 설치된 한글의 같은 키 입력 6가지와 대조합니다. 배치 갱신이 이동한 커서를 이전 위치로 되돌리던 문제를 수정했으며, 조합 중 Ctrl+S는 마지막 음절까지 기본 HWPX에 저장합니다. 아랍어·히브리어 원문 교체에 이어, 그리기용 하이픈이 있는 영어 원문도 한국어로 바꾸고 한 번의 되돌리기로 복원합니다. [줄 나눔 구현 당시의 입력기 기록](research/evidence/paragraph-word-break-ime-runtime.json)은 실제 입력기 검사 4개와 저장 파일 20개를 보존합니다. 이 중 HWP/HWPX 8개를 [설치된 한글에서 다시 열어](research/evidence/paragraph-word-break-ime-native-oracle.json) 원문·문단 설정과 7개 언어의 글자 속성을 확인했습니다. 포터블 실행 파일에서도 실제 운영체제 입력기로 방향키 뒤의 조합 위치를 확인했습니다.

문단 모양의 한글·영어 줄 나눔을 각각 편집할 수 있습니다. 혼합 문단·제목에서 바꾸지 않은 줄 나눔 값은 유지하며 한 번에 되돌립니다. HWPX의 한글 줄 나눔 이름은 실제 한글의 숫자 속성과 대조해 읽고 씁니다. 가져온 예약값은 HWP·FHN에 유지하고, HWPX에 손실 없이 옮길 수 없으면 저장을 중단합니다. 하이픈은 [공개 영어 사전과 이용 조건](licenses/english-hyphenation.txt)을 동봉해 인터넷이나 운영체제 사전 없이 작동합니다. 표시용 하이픈은 저장 원문이나 클립보드 본문에 추가되지 않습니다.

[줄 나눔 구현 당시의 배포 검증](research/evidence/paragraph-word-break-validation.json)은 핵심 검사 106개, UI·데스크톱 검사 113개, 실제 배포 검사 15개와 Windows 입력기 검사 4개를 기록합니다. 실제 배포 앱에서 여섯 조합으로 저장한 HWPX/HWP/FHN 18개 중 [HWPX/HWP 12개](research/evidence/paragraph-word-break-native-oracle.json)를 설치된 한글에서 다시 열어 문단 속성과 원문이 일치했습니다. 한글에는 맑은 고딕, 영어에는 Arial 16pt를 명시한 원본 표본에서 단어·글자 모드의 네 조건은 전체 원문 줄 구성이 일치했습니다. 하이픈 모드의 두 조건은 하이픈을 넣는 위치에 차이가 남습니다. [실제 하이픈 HTML·PDF 출력 두 조건](research/evidence/paragraph-word-break-printing.json)은 수정하지 않은 PDF의 내장 글꼴 문자 매핑과 줄 위치를 독립적으로 읽어 편집 화면의 원문 줄 구성과 대조했습니다.

최소 공백은 [한컴의 설명](https://help.hancom.com/docs/ko-KR/mergedProjects/hoffice_hwp/topics/hancomoffice/hwp/format/paragraph/paragraph%28word_spacing%29.htm)에 따라 25~100% 범위에서 입력하며, 화면의 남은 폭과 파일에 저장하는 축소량을 구분합니다. 줄 끝 낱말이 들어갈 수 있는 범위까지 공백을 줄이고, 필요하지 않은 축소와 문단 첫머리의 공백은 유지합니다. 혼합 문단·제목의 바꾸지 않은 설정은 보존하고 한 번에 되돌립니다. 가져온 예약값은 HWP·FHN에 유지하며, HWPX에서 지원하지 않는 예약값을 바꾼 문서로 저장하려면 지원하는 값으로 변경해야 합니다. 줄 배치를 측정하지 못하는 그림·위아래 첨자·RTL 방향 문단에서는 원본 설정을 파일에 보존하고 기존 공백 폭을 유지합니다. 일반 문단에서도 모든 글꼴·복합 조판이 원본과 완전히 같다는 뜻은 아닙니다.

[최소 공백 구현 당시의 배포 검증](research/evidence/paragraph-minimum-space-validation.json)은 Arial 16pt, 정렬 2종·빈칸 모드 2종·문단 폭 3종·축소량 4종의 48개 조건에서 실제 글자들의 줄 배치가 한글의 원본 줄 정보와 일치했음을 기록합니다. 실제 앱이 저장한 HWPX/HWP/FHN 144개 중 HWP/HWPX 96개를 한글에서 열고 재저장했으며, 같은 HWP 입력 48개는 별도로 한글의 Base64 가져오기·내보내기도 확인했습니다. 문단 숫자와 실제 입력기 표본 16개를 더해 디스크 재열기는 총 112개입니다. 별도 HTML·실제 PDF 두 조건의 줄 배치, 한국어 입력·실행 취소와 실제 Windows 포터블 실행도 확인했습니다. 이 결과는 해당 표본과 Windows 배포본의 검증이며 Mac 실행이나 모든 문서 조판의 일치를 뜻하지 않습니다.

문단 미리 보기는 앞뒤의 회색 문단과 가운데 설정 문단을 따로 배치하며 여백·들여쓰기/내어쓰기·정렬·줄 나눔·문단 간격·비율/고정/0 간격에 반응합니다. 원본 한글처럼 문서의 글자 크기와 별개인 표본을 사용하고, 최소 공백 값만 바꿀 때는 미리 보기의 배치를 유지합니다. 실제 본문의 최소 공백 배치는 계속 별도로 적용합니다. 숫자를 입력하는 도중에는 마지막 유효 미리 보기를 유지하며, 취소하면 문서나 실행 취소 기록을 바꾸지 않습니다. [미리 보기 검증](research/evidence/paragraph-preview-validation.json)은 핵심 109개·화면/데스크톱 123개·실제 배포 앱 18개·Windows 입력기 5개 검사를 기록합니다. [원본 33개 조건의 직접 비교](research/evidence/paragraph-preview-current-captures.json)는 같은 553×642 PNG를 보정하지 않고 검사했으며, 전체 대화상자는 90.15~91.78%, 미리 보기 영역 자체는 71.30~82.94%의 RGB 픽셀이 일치했습니다. 두 독립 디코더의 일치 픽셀 수는 같으며 흰 배경도 포함합니다. Windows의 글자 렌더링 차이와 일부 줄 위치 차이는 남아 있으며 모든 미리 보기 픽셀이나 다른 플랫폼의 일치를 뜻하지 않습니다.

줄 격자는 HWP 문단 속성의 비트 8과 HWPX `snapToGrid`, 구역의 `lineGrid`를 독립적으로 읽고 저장합니다. 일반 본문 문단·제목에서는 양수 줄 진행을 다음 격자 배수로 올리며, 0 간격의 겹침은 유지합니다. 문단 위·아래 간격도 각각 격자에 맞춥니다. 편집 용지의 줄 수·간격 입력은 소수점 한 자리 표시와 원본 정밀도를 구분합니다. 예를 들어 기본 A4에서 20줄을 입력하면 32.9pt로 표시하고 파일에는 32.88pt를 보존합니다. 용지 설정은 본문 문자를 바꾸지 않고 한 번에 실행 취소할 수 있습니다. [줄 격자 검증](research/evidence/paragraph-line-grid-validation.json)은 설치된 한글에서 관찰한 줄 배치 54개·문단 전환 24개·정밀도 경계 7개를 기록합니다. 공개 도움말의 [줄 격자 설명](https://help.hancom.com/hoffice130/ko-KR/Hwp/format/setting_paper/setting_paper%28grid%29.htm)과 [문단별 적용 설명](https://help.hancom.com/hoffice130_assistant/ko-KR/Hwp/format/paragraph/paragraph_general.htm)도 대조했습니다. HWP 저장 범위를 넘는 격자 간격은 잘못된 음수로 저장하지 않고 오류를 알리며 HWPX·FHN에는 보존합니다.

실제 배포 앱이 원본 HWP 85개를 가져온 편집 화면과 직접 저장한 HTML 85개의 상대 줄 위치가 원본 캐시와 일치했습니다. [줄 격자 창 두 상태의 직접 비교](research/evidence/line-grid-current-pixels.json)는 같은 661×682 PNG에서 약 95.98%의 RGB 픽셀이 일치했으며, 이미지 수정·정렬 없이 두 독립 디코더로 검사했습니다. 흰 배경도 일치율에 포함합니다. [실제 PDF 글자 좌표](research/evidence/line-grid-current-pdf.json)는 32.88pt 원본 설정을 포한에서 약 33pt, 별도로 저장한 원본 한글 PDF에서 약 32.8441pt로 측정했습니다. 48pt 문단 전환 표본은 포한 PDF에서도 약 48pt였으나, 소수점 PDF 위치의 완전한 일치는 남아 있습니다.

추가로 원본 한글이 직접 출력한 PDF 85개와 격자 적용 전후 27쌍을 검사해, 논리적인 줄 시작 위치만으로는 실제 글자 위치를 검증할 수 없음을 확인했습니다. 격자로 늘어난 간격의 절반만큼 글자 기준선도 이동하도록 수정했습니다. 예를 들어 48pt 논리적 문단 전환 표본의 실제 글자 간격은 45pt입니다. 기존 캐시 관찰 기록은 유지하며 실제 PDF 관찰과 구분합니다. 원본 PDF는 관찰된 600dpi 정수 좌표와 용지 변환을 사용하므로, 장치 좌표를 원본 단위로 환산해 비교합니다.

HTML의 화면용 원문을 유지하면서 인쇄 시에는 검색 가능한 SVG 글자를 정확한 기준선에 표시합니다. Chromium의 정수 픽셀 원점 반올림을 피하므로 32.88pt가 33pt로 변하던 문제를 수정합니다. 실제 PDF 85개를 독립적인 글꼴 문자 매핑·좌표 판독기로 검사하며, 정확한 원본 단위의 상대 기준선 오차는 0.02pt 이하, 원본 한글 PDF와의 비교는 원본 장치의 한 픽셀과 이 오차를 합한 범위로 검사합니다. 혼합 서식·연결 문자·클릭 가능한 링크, 긴 문단과 분리된 문단의 80줄 페이지 넘김, HTML 재열기의 원문 중복 여부도 검사합니다. 이 검사는 상대 기준선과 해당 표본에 대한 결과이며 모든 글꼴의 잉크·색·장식·절대 위치나 검색기의 RTL 추출 순서 일치를 보장하지 않습니다. [추가 출력 검증](research/evidence/fractional-print-validation.json)에 최종 배포 파일과 검사 결과를 연결합니다.

페이지 첫 줄의 누적 차이는 원본 한글이 출력한 63개 문서의 실제 페이지·줄 캐시와 대조해 수정했습니다. 일반 본문의 인쇄용 페이지는 줄 진행과 마지막 줄의 적합 높이를 구분합니다. 예를 들어 16pt 격자에서 170%의 10pt 줄은 32pt씩 진행하지만, 마지막 줄은 격자에 맞춘 글자 높이 16pt로 판정합니다. 본문 끝과 정확히 같은 위치에 닿으면 다음 페이지로 넘기며, 0.01pt의 여유가 있을 때 허용되는 경계도 검사합니다. 긴 문단·분리된 문단·문단 위아래 간격·강제 쪽 나눔을 별도로 확인했습니다. 편집 원문은 유지하고, 측정한 인쇄용 글자를 원래 용지 여백과 각 페이지의 독립적인 기준선에 배치합니다. [실제 페이지 검증](research/evidence/native-pagination-validation.json)에 최종 실행 파일과 원본·포한의 실제 PDF 관찰을 연결합니다.

비율 줄 간격은 원본의 소수점 글자 크기 49개 조건과 추가 격자 5개 조건으로 대조했습니다. 한글은 원래 글자 높이를 유지하면서 추가 줄 간격을 0.04pt 단위로 계산하며, 양수·음수의 절반 경계와 정수 기준선을 구분합니다. 따라서 19.99pt의 170% 줄은 33.95pt씩 진행합니다. 0%에서도 글자 크기에 따라 0.01~0.03pt의 잔여 진행이 생길 수 있습니다. 예를 들어 10.01pt의 0% 줄은 원본처럼 0.01pt씩 진행하며, 16pt 격자를 적용하면 다음 격자 줄로 이동합니다. 고정 0pt는 계속 완전히 겹칩니다. 이 추가 관찰은 앞선 정수 글자 크기의 0% 겹침 표본과 구분합니다.

측정 가능한 일반 본문의 편집 화면도 같은 물리 페이지 계산을 사용합니다. 원문 문단을 쪼개지 않고 여러 용지·여백 표시·쪽 이동과 현재 커서의 쪽 번호를 갱신합니다. 원본 PDF 63개 조건의 실제 화면 글자 위치와 쪽 배치를 비교하며, 3개 조건은 50~200%의 7개 배율에서도 확인합니다. 쪽 경계의 방향키·Home·End·부분 선택·입력·문단 나누기·되돌리기와 저장 원문 보존을 검사합니다. 빈 줄의 실제 브라우저 커서도 다음 용지로 이동하며, 이 위치에서 실제 Windows 한국어 입력기와 HWPX/HWP/FHN 저장도 확인했습니다. 용지 사이의 간격은 설치된 한글의 125% 화면을 직접 관찰한 값입니다. [여러 쪽 편집 검증](research/evidence/editable-sheets-validation.json)에 실제 배포 파일과 검사 결과를 연결합니다. 모든 배율·글꼴·DPI의 전체 화면 픽셀 일치를 뜻하지 않습니다.

본문 원점을 맞춘 첫 단계에서는 배경색 본문도 종이 위쪽이 아닌 실제 본문 여백을 기준으로 줄 격자를 시작합니다. 격자를 끈 경우에도 문단 위·아래 간격을 각각 보존하고, 배율에 따른 실제 브라우저 정밀도로 문단 높이를 반올림해 축소 화면의 누적 오차를 줄입니다. 기존 보정값이나 CSS 문자열의 반올림 오차를 다음 프레임에 더하지 않아 커서 위치도 안정적으로 유지합니다. 원본 한글의 배경색 문서 18개는 기본·0·소수 머리말/꼬리말과 격자·문단 간격을 조합한 표본입니다. 첫 물리 본문의 실제 글자 위치를 7개 배율과 독립 HTML에서 비교합니다. 단색 글자 배경의 인쇄는 배경과 검색 가능한 글자를 각각 원래 줄의 물리 페이지에 배치해 쪽 경계에서 글자가 중복되던 문제도 수정합니다. 원본 PDF의 배경과 글자가 서로 다른 용지·장치 좌표 변환을 사용함을 확인해 별도로 적용하며, 해당 표본의 80줄 전체 쪽 배치·글자 기준선과 단색 배경의 네 변을 실제 PDF에서 독립적으로 판독해 원본과 0.14pt 이내로 비교합니다. [본문 원점 검증](research/evidence/native-body-grid-origin-validation.json)은 해당 표본의 화면 첫 본문과 실제 인쇄·원문 보존에 대한 검사이며, 배경색 본문의 여러 용지 편집이나 모든 배경 효과·글꼴의 일치를 뜻하지 않습니다.

불투명 단색 글자 배경은 편집 화면에서도 각 물리 용지에 따로 표시합니다. 원문 문단과 글자 색 속성을 유지하면서 배경 표시만 편집 원문 바깥에 배치해, 여러 쪽에 걸친 선택·입력·한 번의 실행 취소와 HWPX/HWP/FHN 저장을 검사합니다. 원본 배경색 문서 18개의 모든 쪽 글자 위치를 7개 배율에서 대조하며, 125% 화면 6개는 원본의 실제 배경색 픽셀 경계와 비교합니다. 커서가 가린 가장자리와 글자 안티앨리어싱은 이 비교의 일치 판정에 포함하지 않습니다. 16pt·24pt와 상대 크기를 바꾼 원본 화면도 추가 관찰해 커서 아래 여백과 원래 글자 크기에 따른 배경 높이를 구분했습니다. 실제 Windows 입력기가 빈 다음 용지에 한글을 조합하는 동안에도 원문 DOM을 교체하지 않고 배경 폭을 갱신합니다. 음영이 있는 문장 끝의 공백 뒤에서도 실제 커서 위치로 쪽 번호와 스크롤을 유지하며, Electron과 미리 보기 브라우저의 배경 표시를 각각 원본 화면으로 비교합니다. 선택 범위를 교체할 때 첫 글자가 빠지는 문제와 줄 바꿈 보정의 프레임 반복, 대화상자 종료 뒤 선택 범위가 초기화되는 문제도 수정했습니다. 음영이 없는 문서에서는 불필요한 클래스 갱신을 반복하지 않아 최소 공백 계산이 정상적으로 끝나며, 빠른 정렬 변경과 그 뒤의 타이핑도 독립적으로 실행 취소합니다. [음영 여러 쪽 편집 검증](research/evidence/editable-shading-validation.json)에 검사 결과와 실제 배포 파일을 연결합니다. 16pt Arial의 가로 폭 1픽셀 차이는 아직 추가 작업이 필요합니다.

상대 크기 50%·150%의 16pt 글자와 일반 16pt·24pt 글자는 설치된 한글에서 실제 PDF로 저장해 인쇄 배경을 추가 대조했습니다. 인쇄용 음영도 표시된 글자 크기와 별개로 원래 글자 크기의 높이를 유지하도록 수정했습니다. 네 원본 PDF의 320개 배경 사각형과 모든 물리 쪽의 글자 위치를 대조하며, 7개 화면 배율과 실행 스크립트가 없는 HTML의 실제 PDF 출력도 검사합니다. [상대 크기 인쇄 배경 검증](research/evidence/relative-shading-validation.json)에 원본 관찰과 실제 배포 앱 결과를 연결합니다.

작은 배율의 한 쪽 문서와 여러 쪽 문서, 짝수·홀수 창 높이, 네 가지 용지 크기를 설치된 한글의 실제 화면 82개로 추가 대조했습니다. 용지 주변 여백과 쪽 사이 간격은 배율에 따라 함께 바뀌고, 용지 테두리는 화면에서 같은 두께를 유지합니다. 창 크기를 바꾼 뒤에도 음영을 실제 픽셀에 다시 맞추며 세로 눈금 원점을 용지와 연결합니다. 창 너비가 달라진 뒤 아래 화살표를 누르면 커서가 줄 끝으로 뛰던 문제는 용지 기준의 글자 열을 유지하도록 수정했습니다. [용지 화면·크기 변경 검증](research/evidence/native-paper-viewport-validation.json)에 원본과 실제 배포 앱의 검증 범위를 기록합니다. 일부 원본 캡처의 하단은 그려지지 않아 해당 이어지는 경계는 미관측으로 남깁니다. 글자 가로 폭, 여러 쪽의 세로 눈금 반복과 전체 UI 일치는 계속 추가 작업이 필요합니다.

폭 맞춤·쪽 맞춤은 창 크기, 도구 상자 높이와 용지 방향이 바뀌어도 유지됩니다. 배율 표시도 원본처럼 맞춤 모드를 표시하며, 숫자 배율 적용이나 확대·축소는 수동 배율로 전환합니다. 보기 대화상자 취소는 맞춤을 유지하고, 보기 변경은 본문이나 실행 취소 기록에 들어가지 않습니다. 설치된 한글에서 모드를 한 번 선택한 뒤 실제 창 크기를 바꾼 36개 상태의 배율·모드 표시·용지 경계를 [맞춤 화면 표본](tests/fixtures/native-fit-viewport.json)으로 보존했습니다. 이 표본은 글자 가로 폭, 전체 UI 또는 Mac 실행의 일치를 뜻하지 않습니다.

가져온 글자 격자와 원고지 정서법 값은 보존하지만 가로 조판은 아직 구현하지 않아 해당 설정은 읽기 전용입니다. 편집 화면의 새 물리 페이지 투영은 전체 본문을 측정할 수 있는 일반 문단·제목과 불투명 단색 글자 배경에 적용합니다. 인쇄도 단색 글자 배경을 별도로 투영합니다. 표·그림·문단 전체 배경·복합 배경 효과·별도 윤곽선/장평 그림처럼 아직 페이지에 투영하지 못하는 내용이 있으면 기존의 출력 경로를 유지합니다. 제목과 다음 문단의 연결처럼 아직 투영하지 못한 쪽 나눔 제약이 실제로 걸리는 경우에도 기존 연결을 유지합니다. 이 경우의 네이티브 페이지 일치는 아직 구현·검증하지 않았습니다. 표·목록·여러 구역의 줄 격자 배치와 여러 용지 편집, 서로 다른 서식을 가로지르는 영어 하이픈, 다른 문자권의 하이픈, 모든 대체 글꼴과 문단 미리 보기의 완전한 일치도 추가 작업이 필요합니다. 전체 UI 100% 일치와 세 환경의 전체 배포 검사 통과는 아직 달성하지 못했습니다. 이전 기록에는 각 기록이 실제로 검사한 배포 파일의 해시가 유지됩니다.
